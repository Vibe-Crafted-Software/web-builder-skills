# Website Search (Pagefind)

Add real, on-site full-text search — with category filtering and
sorting — to a content-heavy client site, using
[Pagefind](https://pagefind.app): a static, build-time search index with
a zero-backend runtime (WASM + content-hashed JSON chunks). Layers on top
of `website-build-standards`; doesn't replace it.

## Scope

Use this for sites where a nav/sitemap alone isn't enough to find
things — documentation sites, knowledge bases, large blog/article
archives (dozens to hundreds of pages). **Not** for a typical small
client marketing site (5–15 pages) — those don't need it, and shouldn't
take on this skill's one build-step exception for no real benefit.

## The one exception to "no build step"

`website-build-standards` is deliberately build-tool-free. This skill is
the one documented exception: Pagefind's *index* is generated by a small
Node script, run at build/deploy time. That's the only place Node
tooling enters the picture — the **shipped site** is still plain static
HTML/CSS/JS plus Pagefind's own generated assets under `/pagefind/`. No
runtime backend, no third-party service, nothing the browser talks to
except the same static host. Keep the Node tooling under something like
`tools/` with its own `package.json` and a gitignored `node_modules/`, so
it never gets confused with the deployed site.

Dependencies: `pagefind` (the Node indexing API, not the CLI — see
below).

## Header integration

Builds on `website-build-standards`'s `.site-header__actions` flex group
(logo pinned left, everything else pinned right via `justify-content:
space-between` on `.site-header__inner`). That skill documents a
`.theme-toggle` *script* but no button markup — this skill is where the
toggle's actual `<button>` (sun/moon SVG icons) gets defined, so search
and the toggle can share one row.

Order, left to right, right-aligned as a group: **search form → any
other header buttons (e.g. a feedback trigger) → theme toggle**. The
search box is a plain `<form action="/search/">` with a single `name="q"`
input — Enter/submit navigates to the results page natively, no JS
required for that part:

```html
<div class="site-header__actions">
  <form class="site-search" action="/search/" role="search">
    <label class="visually-hidden" for="site-search-input">Search</label>
    <input class="site-search__input" id="site-search-input" name="q" type="search" placeholder="Search...">
  </form>

    <svg class="theme-toggle__icon--light" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round" aria-hidden="true"><circle cx="12" cy="12" r="4"></circle><path d="M12 2v2M12 20v2M4.93 4.93l1.41 1.41M17.66 17.66l1.41 1.41M2 12h2M20 12h2M6.34 17.66l-1.41 1.41M19.07 4.93l-1.41 1.41"></path></svg>
```

- `.site-search { flex: 1; max-width: 26rem; }` — grows to fill the row
  without ever crowding out the toggle.
- `/` focuses the input from anywhere on the site (GitHub/Stripe-style),
  unless focus is already in an input/textarea/select/contenteditable.
- The toggle button's own click handler and dark-mode CSS are exactly
  `website-build-standards`'s existing (markup-less) `.theme-toggle`
  script — this skill only adds the button/SVG markup around it.

## Dedicated `/search/` results page

A dropdown was tried on the reference implementation and explicitly
replaced — use a real page instead. Two-column layout: category
checkboxes on the left, results + toolbar on the right (result count,
`Sort by` — Relevance / Title A–Z).

- **Category tagging**: a hidden `<span hidden
  data-pagefind-filter="category">CategoryName</span>` inside each page's
  indexed content wrapper. This one attribute drives both the checkbox
  list and the live per-category result counts — keep it in sync with
  however the site derives "category" (its top-level nav/folder segment,
  in the reference build).
- **Indexing scope**: only wrap the real content region in
  `data-pagefind-body` — never the header, nav, or footer, or they'll
  pollute every result. A page that should never appear in search (a 404
  page, an unlisted style-guide page) simply omits the attribute.
- **Search logic** (`search-page.js`, loaded only on `/search/`): reads
  `?q=` + repeated `&category=` + `&sort=` from the URL, dynamically
  imports `/pagefind/pagefind.js`, and calls:

  ```js
  pagefind.search(query, { filters: { category: selectedCategories } })
  ```

  **Always pass an explicit array here, even `[]`** — that's what makes
  Pagefind populate `search.totalFilters.category` with a live
  per-category count for the current query *without* narrowing results.
  Omitting `filters` entirely leaves those counts empty. This is the one
  non-obvious detail in the whole implementation.
- **Sort**: "Relevance" is Pagefind's own ranked order, untouched.
  "Title" is a plain client-side `localeCompare` over the already-fetched
  `result.data()` array — not a Pagefind-side sort option, which would
  need an extra indexed attribute for no real benefit at this scale.
- **URL state**: every change (query, category checkboxes, sort) calls
  `history.pushState` with its own query-string scheme (`?q=...&category=
  A&category=B&sort=title`, repeated params for multi-select); a
  `popstate` listener re-runs the search on back/forward. The result:
  every search state is bookmarkable and shareable as-is.

Full page template + `search-page.js` → `references/website-search.md`.

## Build-time indexing

A small Node script (not the `pagefind` CLI) rebuilds the index from
whatever HTML is currently on disk:

```js
const pagefind = await import("pagefind"); // ESM-only
const { index } = await pagefind.createIndex({});
// walk the site's own HTML files yourself (see reference for the exact
// walk) and call index.addHTMLFile({ sourcePath, content }) per file
await index.writeFiles({ outputPath: "pagefind" });
await pagefind.close();
```

Use your **own file walk**, not the `pagefind` CLI's `--site .` walk —
the CLI would also discover anything else living under the repo root
(a `tools/` cache, `node_modules` fixtures), which you don't want
indexed. Skip `tools/`, `.git/`, and `node_modules/` explicitly.

- Run this as the **first step** of the site's deploy script, every
  time, so a hand-edited or newly-added page is never deployed
  un-indexed — no separate "remember to reindex" step to forget.
- **Expect churn in `/pagefind/` on every reindex, even with zero content
  changes** — Pagefind's internal chunk boundaries aren't purely
  content-deterministic across runs, so a handful of `fragment`/`index`/
  `filter` files routinely get new hashes each time. Normal, not a bug.
- **Delete Pagefind's own prebuilt UI bundles** right after
  `writeFiles()` — `pagefind-ui.*`, `pagefind-component-ui.*`,
  `pagefind-modular-ui.*` are dead weight once you're building a fully
  custom UI on the low-level API, which this skill always does.

Full reindex script → `references/website-search.md`.

## Deploy caching (extends `website-deployment`)

`website-deployment`'s routine deploy is two passes — assets long-cache
immutable, everything else short/no-cache — because the base stack has
no content-hashed filenames. Pagefind's output splits across both passes
differently from a normal asset:

- **Join the long-cache/immutable pass**: `pagefind/fragment/`,
  `pagefind/index/`, `pagefind/filter/` — genuinely content-hashed, a
  changed file gets a new name.
- **Join the short-cache/must-revalidate pass** (with the HTML and
  `main.js`/`main.css`): `pagefind/pagefind.js`, `pagefind-worker.js`,
  `pagefind-entry.json`, `*.pf_meta`, `wasm.*.pagefind` — same filename
  every rebuild, so a long-cached copy would keep serving stale search
  code after a reindex.

## Verification checklist

- A real query returns ranked results (test at least one deliberate
  typo — Pagefind's fuzzy matching should still rank the right page
  top-of-results).
- Checking a category narrows results and its facet count updates live,
  without a full page reload.
- The sort select reorders results without re-querying Pagefind.
- `/` focuses the header search input from anywhere except inside a text
  field.
- Browser back/forward reproduces the exact prior query/filter/sort
  state.
- A bookmarked `/search/?q=...&category=...&sort=...` URL reproduces the
  same results on a fresh load.
- The reindex script runs as the first step of deploy, so content edits
  can't ship un-searchable.
- `data-pagefind-body` wraps only real content — confirm header/nav/
  footer text doesn't show up in a result excerpt.
